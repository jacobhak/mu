`todo` NEVER takes a turn of its own: emit it in the same response as your next real tool call (parallel tool calls), `init` beside the first read or action, `done`/`start` beside the next action or check. A response whose only call is `todo` wastes a full model round trip.
Tasks identified by verbatim content, NEVER generated IDs (task-1). Unique, stable task/phase names; lost text: view, NEVER guess. `task` names one task, `tasks` several in one call, `phase` every task in that phase; `done`/`drop`/`rm` with none of them act on the whole list.
Before work, init for 3+ steps, requested task sets, or new instructions. MUST list EVERY user item separately (phased/numbered/bulleted/N); NEVER omit or remember leftovers.
The list tracks progress as it happens; it is not a summary written afterwards. `start` a task before its first action, and `done` it in the response right after its work finished, beside the next task's `start` or the next action. Pass them together as `tasks` when several really finished at once (parallel results, one edit), but NEVER `done` a task you did not `start`, and NEVER tick the list off at the end: a list that goes from pending to all done in one step is a misuse.
After successful mutation: no active means earliest pending starts (phase order); multiple active means only earliest stays. Blocked NEVER starts automatically; unblock returns pending. Done out of order may rewind pointer but NEVER reopen completed. Follow phase order.
External waits (user/agent/service): block with optional reason suppresses stop reminder, starts next pending. Unblock when actionable; append a clearing task for agent-actionable blocker.
